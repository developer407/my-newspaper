Claude platform and models

Fable 5.2 migration notes: the API behaviours that can return HTTP 400

Claude Platform release notes · Nov 9, 2026

Beyond the headline $8 / $40 pricing, the Fable 5.2 and Mythos 5.2 notes list changes that break older request patterns. A prefix check is enforced on every account, the older computer-use tool returns a 400, and thinking blocks only work in the account that produced them.

💡 Why it matters to you: If your Spring AI or Python agent edits earlier messages or tools between turns, or reuses stored thinking blocks, test it against claude-fable-5-2 before switching the model name.
Read deeper

Prefix check: if you edit the system prompt, the tools, or earlier messages and then send back a later thinking block, the request returns a 400. Computer use needs the computer_toolset_20260801 toolset; the older computer_20251124 tool returns a 400 except on Amazon Bedrock.

Thinking blocks from these models work only in the account that produced them (or a linked account). Fable 5.2 and Mythos 5.2 can read thinking blocks from other models on the Claude API and Google Cloud, but moving to any other model drops them (the request still succeeds). Both models require 30-day retention and are not available under zero data retention unless Anthropic authorizes it.

Other items from the same notes: fast mode for Fable 5.2 costs $16 input / $80 output per million tokens and is enabled with speed: "fast" with no beta header; an advisor tool (beta) lets a Fable 5.2 or Mythos 5.2 executor use only those two models as advisor; Dreams now supports Fable 5.2 as a research preview. Mythos 5.2 is limited to verified organizations.

// Fast mode on Fable 5.2 (Claude API), per the release notes
{ "model": "claude-fable-5-2", "speed": "fast", "max_tokens": 1024, "messages": [ ... ] }

Linked billing (beta): let your customers pay for Claude usage through their own organization

Claude Platform release notes · Nov 17, 2026

A new beta lets customers pay for Claude usage in your app through their own Claude organization. You enable it with the user-profiles-billing-2026-10-01 beta header and choose who pays with billing_policy on each request.

💡 Why it matters to you: For an AI SaaS you teach or sell, this is a way to ship a bring-your-own-Claude-plan app without carrying every user's inference bill.
Read deeper

The setting goes on each /v1/messages or /v1/chat/completions request. Customers can set a spend cap or unlink your app in the Claude Console. The notes say it works only for customers whose organization pays Anthropic directly for API usage.

The release note does not list the accepted billing_policy values in the summary, so read the full docs entry before building on it. It is a beta, so expect the shape to change.

A natural fit is a Spring Boot backend that proxies Claude calls and stamps the policy per user, with a React settings page for linking and unlinking.

Message threads (beta): keep conversation state on the server and send only new messages

Claude Platform release notes · Nov 2, 2026

With the message-threads-2026-08-12 beta header, Claude keeps conversation state on the server so later requests send only the new messages. Threads expire 5 minutes after their last request and are deleted no later than 1 hour after last use.

💡 Why it matters to you: It could shrink the payloads your chat endpoints resend on every turn, but the 5-minute expiry means you still need a fallback that rebuilds history yourself.
Read deeper

The short lifetime is the key design constraint. A user who pauses for ten minutes comes back to an expired thread, so a robust app still stores the transcript (for example in Postgres) and can replay it.

In Spring AI terms this sits next to ChatMemory and the session-memory work in the 2.1 line: server-held state is an optimization, not a replacement for your own conversation store.

anthropic-beta: message-threads-2026-08-12

Text watermarking now covers more Claude models, and non-default sampling can switch it off

Text from Claude Opus 4.6, Opus 4.5, Sonnet 4.5 and Haiku 4.5 now carries Anthropic's text watermark on supported platforms (Nov 16), after Mythos 5, Opus 4.7 and Sonnet 4.6 (Nov 3). If a request sets temperature, top_p or top_k to a non-default value, the watermark might not appear.

💡 Why it matters to you: If you set temperature in Spring AI or LangChain options for a Claude model, you may be opting out of the watermark without noticing.

The notes say the watermark is applied on supported platforms, and that on Sonnet 4.6 non-default sampling parameters might also stop it from appearing. The wording is hedged ("might not"), so do not assume either outcome.

MCP and protocols

MCP reference servers 2.5.0 fixes eight more vulnerabilities in the git, filesystem and everything servers

modelcontextprotocol/servers GitHub releases · Nov 18, 2026

The v2.5.0 security release fixes eight vulnerabilities across three servers. mcp-server-git 2026.11.18 stops automatic maintenance after a merge, refuses index entries that point outside the working tree and no longer lets submodule configuration run programs.

💡 Why it matters to you: If any of your agents or Claude Code configs run these reference servers, update them; date-versioned npm packages need an explicit install.
Read deeper

server-filesystem 2.4.0 anchors directory listings to the checked directory on Linux and macOS (Windows is not yet covered), and server-everything 2.3.1 makes the gzip-file-as-resource tool check the IPv4 address embedded in NAT64 addresses.

The release warns that users on date-versioned npm releases must install 2.4.0 explicitly, because package managers will not offer it as an upgrade. This follows v2.4.0 on Nov 11, which fixed six vulnerabilities in the filesystem, git and fetch servers.

Pattern to take away: tools that touch the filesystem or git on an agent's behalf are a real attack surface, so pin versions and run them in a sandbox or container.

# pin the date-versioned packages explicitly
npx -y @modelcontextprotocol/server-filesystem@2.4.0 /path/to/allowed/dir

MCP SDK 2.x tightens security: same-origin redirects, session caps and OAuth issuer checks

modelcontextprotocol python-sdk and typescript-sdk releases · Sep 7 - Oct 23, 2026 (catch-up)

The Python SDK 2.2.0 and 2.3.0 and the TypeScript SDK 2.4.0 add several hardening changes: same-origin redirect following, idle session expiry, a cap of 10,000 concurrent sessions, and OAuth issuer validation. Tools with invalid x-mcp-header annotations now fail at registration.

💡 Why it matters to you: If you build or consume MCP servers from Spring AI or Python, these defaults change how your clients behave on redirects and sessions.
Read deeper

Python SDK 2.2.0 (Sep 7): HTTP clients follow redirects only within the same scheme, host and port; idle Streamable HTTP sessions expire after 30 minutes on the legacy spec; the OAuth client validates the authorization server issuer. 2.3.0 (Oct 2) adds max_sse_event_size and makes invalid x-mcp-header tools fail at registration instead of being silently dropped.

TypeScript SDK 2.4.0 (Oct 23) adds an opt-in scopeForRefresh(tokens) for authorization servers such as Microsoft Entra ID that reject token refreshes without a scope. Breaking: x-mcp-header on number parameters is now rejected, and outputSchema results for 2025-11-25 connections are no longer wrapped in { result }.

These are older than the 48-hour window, but they are the ones that change behaviour you may meet when you upgrade MCP libraries.

Paper: comparing three ways to evaluate enterprise analytics agents (arXiv 2611.14493)

arXiv · Nov 10, 2026 (via search summary)

A comparative study evaluates enterprise analytics agents with three setups: trace-based LLM judging, text-only judging with red-teaming, and deterministic heuristics. It reports that the information available to the evaluation harness determines evaluation quality, and that functional and security evaluation are complementary.

💡 Why it matters to you: For a RAG or agent project you teach, this supports using several checks (traces, adversarial prompts, plain assertions) rather than one LLM judge.
Read deeper

I could only see an abstract-level summary through search, so details such as datasets and numbers are not covered here. Read the paper before quoting it.

A related paper, arXiv 2605.27898 (revised July 2026), proposes a unified setup for comparing agent benchmarks and finds that scores shift when existing benchmarks are re-run under a common scaffold, so published scores mix model ability with implementation choices.
