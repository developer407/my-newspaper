Model releases & the open-weight race

Anthropic: new defenses cut distillation of Claude's reasoning by 90–99%

Anthropic · Oct 12, 2026 (catch-up: slower-moving, still new to this paper)

Anthropic reports that a new set of safeguards has sharply reduced how much reasoning data illicit distillers can harvest from Claude — early evidence says 90–99%, with distiller-extracted reasoning tokens down 10–100x on Anthropic's own platform. The defenses are tighter control over where reasoning can travel, a two-stage extraction classifier, and harsher consequences for repeat offenders.

💡 Why it matters to you: If your Spring AI or LangGraph app replays Claude reasoning, 'preserved thinking' and the org-only reasoning visibility rules can change how you store and resend context — and blocked requests are now billed.
Read deeper

Details from the post: 'preserved thinking' (introduced with Claude Fable 5.1 and Opus 5.5) stops API accounts created on or after Aug 31, 2026 from editing Claude's prior context, and with Claude Sonnet 5.5 reasoning transcripts are visible only to the organization whose request produced them. A two-stage classifier built on Anthropic's constitutional-classifier research detects extraction attempts, reportedly with a false-positive rate under 0.1% — and since Sept 24 requests blocked by safeguards before Claude responds are charged.

Anthropic also describes the scale of the abuse it is fighting: proxy networks with hundreds of thousands of fraudulent accounts (one ran 20,000+ at once) and tens of thousands of bans, often within two hours of a campaign starting. The post is explicit that developers may need to update integrations to adopt preserved thinking, and that this is expected to be a cat-and-mouse game.

Practical takeaway for builders: don't mutate or re-order reasoning blocks you receive from the API, don't forward them across accounts or to other models, and treat an unexpected 'blocked' response as a signal to review what you are sending rather than just retrying.

Spring AI Modular RAG + Jev: rewrite the query, filter the chunks, then answer

Spring Blog (Christian Tzolov) · Oct 2, 2026

A step-by-step recipe turns Spring AI's RetrievalAugmentationAdvisor into a modular pipeline: rewrite and expand the question, retrieve per query, then run a 'Jev' filter and reranker over each chunk before the generation step. In the demo, six retrieved chunks were cut to the two that actually answered the question, and every passage was screened for prompt injection.

💡 Why it matters to you: This is the cleanest published pattern for production RAG in Spring AI: it directly attacks the two failure modes you hit in client projects — chatty questions and 'similar but useless' chunks.
Read deeper

The pipeline uses swappable interfaces: RewriteQueryTransformer and MultiQueryExpander (pre-retrieval), VectorStoreDocumentRetriever with a 0.5 similarity threshold and topK 4, then JevDocumentFilter and JevDocumentReranker as post-processors, and ContextualQueryAugmenter for generation. The filter asks four questions per passage (prompt injection >0.70 excluded, premise contradiction >0.70 kept but tagged CONFLICTING, relevance <0.45 excluded, answer evidence >0.55 kept), then the reranker keeps the top K.

Gotchas listed in the post: the default retrieval executor uses non-daemon threads so a CLI app may not exit (pass Boot's TaskExecutor; virtual threads work with spring.threads.virtual.enabled=true); newer Claude models reject temperature 0 (HTTP 400) so the demo clones the ChatClient builder for the rewrite calls; if the Jev API is unreachable the pipeline fails open and logs a warning; and it adds two LLM calls before retrieval plus one Jev call per chunk, so measure latency.

var modularRag = RetrievalAugmentationAdvisor.builder()
    .queryTransformers(RewriteQueryTransformer.builder()
        .chatClientBuilder(ragClientBuilder).build())
    .queryExpander(MultiQueryExpander.builder()
        .chatClientBuilder(ragClientBuilder).numberOfQueries(3).build())
    .documentRetriever(VectorStoreDocumentRetriever.builder()
        .vectorStore(vectorStore).similarityThreshold(0.5).topK(4).build())
    .documentPostProcessors(
        JevDocumentFilter.builder(typeSafeClient).build(),
        JevDocumentReranker.builder(typeSafeClient).topK(3).build())
    .queryAugmenter(ContextualQueryAugmenter.builder()
        .allowEmptyContext(true).build())
    .taskExecutor(taskExecutor)
    .build();

Spring AI 2.1.0-RC1: Session Memory replaces ChatMemory, plus tool-call confirmation

Spring AI release notes · Oct 23, 2026 (and Spring blog, Nov 10 roundup)

Spring AI 2.1.0-RC1 introduces Session Memory — an event log with turn-aware compaction — and deprecates ChatMemory. The same release adds tool-call confirmation, migrates the OpenAI and DeepSeek chat models to message parts, and adds overlap support to TokenTextSplitter. Craig Walls published a migration recipe that the Nov 10 'This Week in Spring' highlights.

💡 Why it matters to you: If your chatbot uses ChatMemory today, this is the migration to plan before 2.1 GA — and tool-call confirmation is exactly the human-in-the-loop hook agent demos need.
Read deeper

RC1 also gives OpenSearch upsert and query-embedding search and makes unsupported upsert/vector-search calls fail fast, and bumps Kotlin to 2.4.21 and Tika to 4.0.0. RC2 (Nov 5, covered in our previous edition) then layered DecisionModel and the stateless MCP server on top.

An event-log memory with compaction means conversations are stored as a sequence of turn events that can be summarised or trimmed per turn instead of a flat message list — useful for long-running agents where you want to keep tool results but drop chatter. Check the Walls recipe for the concrete API before migrating, since this is still a release candidate.

Pin the milestone you test against and read the deprecation notes: ChatMemory is deprecated rather than removed, so there is time, but new code should start on Session Memory.

Agents, SDKs & frameworks

Agent Skills moves to the Agentic AI Foundation — 70+ platforms, ~1M skills

Anthropic · Oct 22, 2026

Anthropic is donating the Agent Skills open standard to the Agentic AI Foundation (AAIF, under the Linux Foundation), which already hosts MCP. The name, logo, GitHub org and agentskills.io domain move to the project; Anthropic cites 70+ agent platforms (including ChatGPT, Cursor, GitHub Copilot and VS Code), about 1 million published skills and nearly 280 million installs.

💡 Why it matters to you: A SKILL.md folder you write once now works across most coding agents — an ideal, low-effort packaging format for your tutorials, internal playbooks and Spring/React conventions.
Read deeper

A skill is a folder built around a SKILL.md with required name and description frontmatter, optionally with scripts and reference files. The proposed roadmap includes versioned releases, a formal proposal process and security guidance for people who write and install skills — important because skills can ship scripts. David Soria Parra and Mahesh Murag are Lead Maintainers.

The anthropics/skills repository (about 195k stars) holds example skills — including the docx, pdf, pptx and xlsx skills — and can be added in Claude Code with /plugin marketplace add anthropics/skills.

Security note: treat third-party skills like third-party code and read the scripts before installing.

description: Our Spring Boot 4 project conventions: package layout, validation, error handling and test style
---

# Spring Boot conventions
1. Controllers return DTO records, never entities.
2. Use Testcontainers for integration tests.

MCP Java SDK 2.2.0-M2: the 'modern' stateless server keeps growing

modelcontextprotocol/java-sdk · Nov 13, 2026

The Java MCP SDK's second 2.2.0 milestone enforces required client capabilities in the modern server, validates SEP-2243 Mcp-Param headers, adds putAll(Map) to McpTransportContext and fixes a tools-list filter race. A breaking change: find returns a handler in modern server repositories.

💡 Why it matters to you: Spring AI's MCP support sits on this SDK — the stateless server for spec 2026-07-28 is what your Java MCP servers will run on, so these are the details that will surface in Spring AI 2.1.
Read deeper

2.2.0-M1 (Oct 16) introduced the modern stateless server in io.modelcontextprotocol.modern, independent of the legacy McpSchema: 'each request is handled on its own' with no sessions. Not yet supported there: a modern client, tasks and SEP-2243 custom headers. The M2 release adds header validation and requires a numeric port for wildcard Host/Origin matching — a security-minded tightening.

The stable line is 2.1.0 (Oct 16): tool-list filtering, Publisher-based HTTP client transports, Streamable HTTP session sweeping/keep-alive, and removal of the 2024-11-05 protocol from Streamable HTTP. Backports 1.1.5 and 0.18.5 keep older lines patched.

If you run MCP servers behind a gateway, the stateless design is the big win: no sticky sessions, so any replica can serve any request.

'Plain RAG beats agent memory': two October papers question complex memory systems

arXiv 2610.34073 & 2610.30755 · Oct 22–25, 2026 (via secondary write-ups; not read in full)

Two recent papers compare dedicated agent-memory systems with simple retrieval over raw history. 'Memory Tax' reportedly tests 11 memory systems and finds many underperform naive RAG, and 'Is Complex Agentic Memory Always Needed?' reports Raw-RAG ranking first in six of seven benchmark-model settings across LoCoMo, LongMemEval, MEME and MemoryAgentBench.

💡 Why it matters to you: Before you add a fancy memory layer to a LangGraph or Spring AI agent, benchmark a plain pgvector/Qdrant retrieval over the raw conversation first — it may win.
Read deeper

Plain-language reading: agent 'memory' systems summarise or restructure past interactions, and every transformation can lose details. Simple dense retrieval keeps the original text and often finds what is needed. Other work (AMA-Bench) reports memory systems underperforming long-context baselines on long-horizon agent tasks, while MemoryAgentBench found no single approach masters all four memory capabilities.

Caveat: I could only read secondary summaries and search snippets for these papers, so treat numbers as indicative and check the arXiv abstracts before quoting them. The finding also fits the practical advice in the Spring Modular RAG recipe — spend effort on retrieval quality and filtering first.
