Tool: Open WebUI 0.13.4 and Tether, a desktop companion that exposes your local models and terminals

open-webui/open-webui releases · Nov 17, 2026 (release page shows the year as 2025; the notes match this week's 0.13.x line)

Open WebUI 0.13.4 replaces Direct Connections with Tether, a desktop companion app that lets your own computer's models, tool servers and terminals appear in Open WebUI without exposing their addresses or keys. Tether can run the local terminal in a sandbox limited to one folder on macOS and supported Windows devices, and local stdio MCP servers can run through it without a proxy such as mcpo.

💡 Why it matters to you: A self-hosted chat UI in front of Ollama plus your own MCP servers is a ready-made demo bench for Spring AI tutorials.
Read deeper

Other additions: Hermes, Antigravity, GitHub Copilot, Goose and Qwen Code join the coding agents available as chat models, pages such as notes and channels open as tabs next to the chat, queued messages are kept on the server and steer an in-progress reply, and the Git panel gains GitHub issue and pull-request management through the GitHub CLI.

Try it with Docker plus Ollama, then connect a local MCP server through Tether instead of exposing a port.

docker run -d -p 3000:8080 -v open-webui:/app/backend/data ghcr.io/open-webui/open-webui:main

Tool: mem0 Python SDK 2.2, structured per-user profiles for agent memory

mem0ai/mem0 releases · Sep 23-25, 2026 (slower topic; check for newer versions)

Mem0 Python SDK 2.2.0 adds User Profiles to MemoryClient and AsyncMemoryClient: structured, LLM-generated per-user summaries shaped by a JSON Schema you configure per project. Generation is asynchronous and an idempotency_key lets you safely retry job requests. 2.2.1 fixes add() so it reports only records the vector store actually inserted and raises VectorStoreError if none were stored.

💡 Why it matters to you: A per-user profile is the simplest memory feature to demo in an AI assistant or resume-coach app, and it pairs with a pgvector store you already know.
Read deeper

The Node SDK 3.3.1 made pg, @types/pg and natural optional peer dependencies, so you must install pg yourself if you use the PGVector store, and fixed OpenAI defaults leaking into other LLM providers.

Before shipping memory, test it against a plain recent-context baseline; the AMA-Bench discussion in The AI Engineer explains why that matters.

pip install -U mem0ai

Idea: a reasoning-aware chat app with Spring AI session memory and a React "thinking" panel

Project idea · builds on Spring AI 2.1 message parts and session memory

Build a chat app where Spring AI 2.1's ReasoningPart is streamed to a React side panel while the answer streams in the main window, with JDBC-backed session memory and turn-count compaction. Offer a model switcher (Claude, GPT, Gemini) to show that reasoning from one provider is skipped by another.

💡 Why it matters to you: It teaches the newest Spring AI feature end to end, with a visible demo and plenty of room for tutorial episodes.
Read deeper

Backend: Spring Boot 4.2, Spring AI 2.1 RC, SessionAdvisors with TurnCountTrigger and WindowCompactionStrategy, spring-ai-starter-model-session-jdbc and Postgres. Frontend: React with Server-Sent Events, a collapsible thinking panel and a conversation list.

Stretch goals: show token usage per turn, add tool-call confirmation, and export a session as markdown.

Idea: a docs-to-RAG assistant for any framework using Firecrawl, pgvector and pre-computed embeddings

Project idea · builds on Firecrawl and Spring AI 2.1 upsert

Crawl a framework's documentation with Firecrawl into markdown, chunk with overlap, embed in a nightly batch job and write the vectors with VectorStore.upsert and stable IDs so reruns update rather than duplicate. Serve answers with citations from a Spring Boot ChatClient and a React UI.

💡 Why it matters to you: It is a sellable pattern (docs chat for a SaaS) and a strong tutorial that covers ingestion, idempotent upserts, retrieval and evals.
Read deeper

Use stable IDs derived from URL plus chunk index, store the page URL and a content hash in metadata and skip unchanged pages. Add a small eval set of 30 questions and run it in CI to catch retrieval regressions.

Compare hybrid search (Qdrant 1.20 added BM25 scoring on the full-text index) against pure vector search in the same app.

Idea: an MCP hardening checker that scans local MCP servers for Host and Origin validation gaps

Project idea · inspired by this week's Jupyter and Todoist MCP DNS-rebinding advisories

Write a small CLI or Spring Boot app that starts against a local MCP server URL, sends requests with forged Host and Origin headers to the MCP endpoint and every other route it can discover, and reports routes that accept them. Add checks for missing bearer-token requirements on state-changing routes.

💡 Why it matters to you: Security tooling for MCP is a young niche; a checker is a good portfolio project and a natural tutorial and blog topic.
Read deeper

Keep it safe: only scan servers you own, run against localhost, and never rebind to third parties. Output a report with the failing route, the header used and the suggested fix.

Extend it to check that the server binds to 127.0.0.1 by default.

Learn today: verify Razorpay webhooks safely in Spring Boot (HMAC-SHA256 on the raw body, and idempotency)

Learning note · standard Razorpay webhook practice; confirm header names in Razorpay's docs

Razorpay signs each webhook with an HMAC-SHA256 of the raw request body using your webhook secret and sends it in the X-Razorpay-Signature header. Verify it on the raw bytes, compare in constant time, and de-duplicate events by the event ID header so retries do not double-process an order.

💡 Why it matters to you: Payments are a recurring part of your full-stack tutorials, and webhook handling is where most demo apps are insecure.
Read deeper

Common mistakes: parsing JSON first and re-serialising (the bytes change and the signature fails), comparing with equals (timing leak), and processing the same event twice because Razorpay retries on non-2xx responses. Return 200 quickly and process asynchronously.

Test: send a valid signature, a tampered body, and the same event twice; expect accept, reject and ignore. Store processed event IDs in a table with a unique constraint.

@PostMapping("/webhooks/razorpay")
ResponseEntity<Void> hook(@RequestBody byte[] raw,
        @RequestHeader("X-Razorpay-Signature") String sig,
        @RequestHeader("X-Razorpay-Event-Id") String eventId) throws Exception {
    Mac mac = Mac.getInstance("HmacSHA256");
    mac.init(new SecretKeySpec(secret.getBytes(UTF_8), "HmacSHA256"));
    String expected = HexFormat.of().formatHex(mac.doFinal(raw));
    if (!MessageDigest.isEqual(expected.getBytes(UTF_8), sig.getBytes(UTF_8)))
        return ResponseEntity.status(400).build();
    if (!processedEvents.markIfNew(eventId)) return ResponseEntity.ok().build(); // duplicate
    queue.enqueue(raw);
    return ResponseEntity.ok().build();
}
