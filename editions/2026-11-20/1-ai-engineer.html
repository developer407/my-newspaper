Model releases and pricing

Gemini 4 Hydrogen: Google's fast execution model for coding and agents, $1.50 / $7.50 per million tokens

Google (blog, via search results) · Nov 12, 2026 · pricing and limits unverified against the docs

Google released Gemini 4 Hydrogen to developers on Nov 12 through Google AI Studio, Android Studio and the Gemini API (model ID gemini-4-hydrogen). It is positioned as the fast, everyday coding and agentic model in the Gemini 4 family, with the heavier Carbon and Argon models aimed at long-horizon reasoning. Reported pricing is $1.50 per million input and $7.50 per million output tokens, with roughly a 1M-token context window.

💡 Why it matters to you: It is a cheap, fast third option next to GPT-6.2 Sol and Claude Opus 5.5 for your Spring AI Gemini starter, and it is already a model profile in LangChain JS and Pydantic AI.
Read deeper

Reports describe text, image, video, audio and PDF input with text-only output, plus function calling, code execution, computer use and structured outputs. It reportedly does not support the Live API, explicit context caching or image/audio generation, so check that before swapping it into a RAG app that leans on context caching.

Sources disagree on the maximum output length (one lists 1,000,000 tokens, another 65,536), so confirm in Google's API docs before relying on either number. Gemini 4 Argon, the larger sibling, was announced on Sep 30 for a limited set of cyber-defence partners at $2 / $10 per million tokens. Hydrogen is the one you can actually call today.

Pydantic AI 2.69 added Gemini 4 Hydrogen support and @langchain/google 0.2.16 added a gemini-4-neon profile, so framework support is landing quickly.

Spring AI and the JVM

Spring AI 2.1 message parts: reasoning that survives the round trip

Spring blog · Oct 28, 2026 (deep-dive on 2.1.0-RC1; GA still pending)

Reasoning models return reasoning blocks, signatures and encrypted items that must be replayed in order on the next request. Spring AI 2.1 stores an assistant message as an ordered list of sealed MessagePart types (text, reasoning, tool call, tool result, media, unknown) with opaque provider payloads, so multi-turn tool loops stop failing with HTTP 400s.

💡 Why it matters to you: This is exactly the bug you hit when you add Claude or GPT thinking to a ChatClient with tool calling and chat memory; 2.1 fixes the model, and you only change how you read reasoning.
Read deeper

Read reasoning with getReasoning() instead of provider-specific accessors. OpaquePayload(provider, kind, data) carries things like an Anthropic signature or an OpenAI encrypted_content; the originating model replays it unchanged and other models skip it. MessageAggregator merges streamed deltas into the same message a blocking call returns, and the Session advisors store every part of every tool round.

Caveats from the post: messages saved before 2.1 have no reasoning parts, reasoning from one provider is never sent to another, and ChatMemory is deprecated for removal in 3.0.0. Persistence needs the spring-ai-starter-model-session-jdbc starter and a JDBC database.

ChatResponse response = chatModel.call(prompt);

List<String> thoughts = response.getResult().getOutput()
    .getReasoning().stream()
    .map(ReasoningPart::text)
    .toList();

@Bean
ChatClient chatClient(ChatClient.Builder builder, SessionService sessions) {
    return builder.defaultAdvisors(SessionAdvisors.builder(sessions)
        .compaction(new TurnCountTrigger(20),
            WindowCompactionStrategy.builder().lastTurns(10).build())
        .build()).build();
}

Spring AI 2.1: bring your own embeddings with VectorStore.upsert and query-vector search

Spring blog · Oct 28, 2026 (deep-dive; store coverage as of 2.1.0-RC2)

VectorStore.upsert(List<EmbeddedDocument>) stores documents together with vectors you already have, and similaritySearch(float[], SearchRequest) searches with a precomputed query vector. add() still embeds with the store's model; the new methods let you control both sides, which matters for multimodal content such as product photos or a migration from another system.

💡 Why it matters to you: For your pgvector RAG demos this means you can re-use embeddings produced in a batch job or by a non-Spring model instead of re-embedding everything.
Read deeper

EmbeddedDocument pairs a Document with a float[] and rejects empty vectors and NaN or infinite values. Writes in one call are not guaranteed to be transactional, so on failure retry the whole list with the same IDs. A Document needs text or media for stores to persist it, so a common pattern is an empty text value plus a metadata pointer to external storage.

At RC1, PGvector, Redis, Elasticsearch, Qdrant and OpenSearch support both methods; RC2 adds Neo4j, MongoDB Atlas, Typesense, MariaDB and Chroma. Both methods are opt-in defaults that throw UnsupportedOperationException until a store implements them. Indexing and query vectors must come from a model that compares those content types, otherwise dimensions can match while results are meaningless.

float[] vector = multimodalModel.call(new DocumentEmbeddingRequest(photoDocument))
        .getResult().getOutput();
Document row = Document.builder().id(stableIdFromSku).text("")
        .metadata("sku", sku).build();
vectorStore.upsert(List.of(new EmbeddedDocument(row, vector)));

List<Document> hits = vectorStore.similaritySearch(queryVector,
        SearchRequest.builder().topK(12).filterExpression("inStock == true").build());

The MCP 2026-07-28 spec went stateless: what changes for servers, and the new security surface

MCP blog and secondary security write-ups (Akamai, VentureBeat, SecurityWeek) · spec stable Jul 28, 2026 · deep-dive

The 2026-07-28 MCP revision retires the initialize handshake and the Mcp-Session-Id header so a request can hit any server instance behind a plain load balancer, and it mandates OAuth 2.1. Security researchers note that new routing headers such as MCP-Method and MCP-Name and the x-mcp-header mechanism create fresh risks: protocol-confusion (desync) attacks and header data leakage. The legacy deprecation window is 12 months.

💡 Why it matters to you: Spring AI 2.1 and MCP Java SDK 2.2.0 both ship a "modern" stateless server for this spec, so your next MCP server is likely to be stateless by default.
Read deeper

Concretely, Spring AI 2.1.0-RC2 enables it with spring.ai.mcp.server.protocol=MODERN, with WebMVC, WebFlux and STDIO transports, but only the synchronous API (type=ASYNC fails at startup) and no modern equivalent yet for client logging, roots or ping. MCP Java SDK 2.2.0 deprecates roots, sampling and logging initiation APIs following SEP-2577.

Take-away for design: with no session, anything you stored per connection (auth context, tenant, cache) must travel in each request or live in your own store. Validate Host and Origin on every route, not only on /mcp, which is exactly the mistake behind this week's Jupyter and Todoist MCP DNS-rebinding advisories in The Dev Digest.

# application.properties (Spring AI 2.1 RC)
spring.ai.mcp.server.protocol=MODERN
# sync only for now: type=ASYNC fails at startup

Paper explained: why agent memory often loses to a long-context baseline (AMA-Bench)

AMA-Bench evaluates long-horizon memory on machine-generated agent-environment traces rather than chat dialogue. Its authors report that memory techniques that beat long-context baselines on dialogue benchmarks often fall short of those baselines on long-horizon agentic tasks, and they propose AMA-Agent, which beats the strongest memory baselines by 11.16% on average.

💡 Why it matters to you: If you add mem0 or a vector-store "memory" to an agent, measure it against simply stuffing recent context; the paper suggests it may not help.
Read deeper

A related benchmark line (MemoryAgentBench, ICLR 2026) concluded that current methods do not master all four memory competencies, and EvolMem (Jan 2026) found no LLM best across all memory dimensions. The shared point is to evaluate memory on your own agent traces.

A cheap test: replay 50 real sessions with and without memory, and score task success, tokens and latency.
