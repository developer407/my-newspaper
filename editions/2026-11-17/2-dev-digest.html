Hono’s csrf() middleware can be bypassed by Chromium hyperlink-audit pings (fixed in 4.13.16)

GitHub advisory GHSA-46wx-v44x-9hh2 · CVE-2026-126355 · published Nov 1, updated Nov 12, 2026

csrf() only checks requests with the three content types an HTML form can send. Chromium’s <a ping> sends a cross-origin POST with cookies and Content-Type: text/ping, which the middleware ignores, so Origin and Sec-Fetch-Site are never checked. Rated Moderate (CVSS 5.3); upgrade to 4.13.16.

💡 Why it matters to you: If you use Hono (or any CSRF filter keyed on content type) for a Node or edge API, a state-changing GET-like POST endpoint could be hit from another site.
Read deeper

Exposure is limited: Chrome and Edge send these pings, Firefox does not by default, and with default SameSite=Lax cookies the attack needs a same-site origin or SameSite=None cookies. Only endpoints whose effect does not depend on the body are reachable.

Workarounds: reject text/ping in middleware before csrf(), or set session cookies to SameSite=Strict. The same advisory feed on Nov 12 lists two more Hono validator issues.

// block the ping content type before csrf()
app.use("*", async (c, next) => {
  if (c.req.header("content-type")?.startsWith("text/ping")) return c.text("no", 400)
  await next()
})

Security

code-review-mcp-server: command injection in four MCP tools (CVE-2026-68934, High 8.7)

GitHub Advisory GHSA-jq3q-62jc-fqq9 · reviewed Nov 16, 2026

The npm package code-review-mcp-server before 1.5.3 interpolated folderPath and baseBranch into shell strings run with child_process.execSync(), so crafted input (a command separator or $(...)) could run arbitrary commands on the host. The fix uses execFileSync() with argument arrays. There is no workaround except upgrading.

💡 Why it matters to you: It is a textbook case of why MCP servers are an attack surface: an LLM supplies the argument, and a prompt injection can steer it.
Read deeper

The affected tools were getLocalGitDiff, codeReview, createPR and getPRTemplate. The maintainer published the advisory on July 6, and the GitHub Advisory Database reviewed it on Nov 16, so exposure windows are long.

For your own servers (Java or Node): never build a shell string from tool arguments, validate paths against an allow-list and run MCP servers with least privilege.

// vulnerable
execSync(`git diff ${baseBranch}`)
// fixed pattern
execFileSync("git", ["diff", baseBranch])

Keycloak JWT algorithm confusion in the JWT Authorization Grant flow (CVE-2026-11800, fixed in 26.6.4)

GitHub Advisory GHSA-j97h-3f8r-mrjr · added to the database Nov 3, 2026

An attacker with valid client credentials could bypass signature verification in Keycloak’s JWT Authorization Grant flow, forging an assertion and obtaining tokens to impersonate any federated user linked to the affected Identity Provider. Rated High (CVSS 8.1). All versions before 26.6.4 are affected.

💡 Why it matters to you: Keycloak is the common OAuth2 server for Spring Security resource-server demos; check your container tag.

Zip Slip in zt-zip (CVE-2026-63436, High) and the Gradle Shadow plugin (CVE-2026-75598, High)

GitHub Advisories GHSA-52c6-99qm-3hqr and GHSA-rr8v-fxxf-c986 · added Nov 9, 2026

org.zeroturnaround:zt-zip before 1.18.0 has a path traversal in its Zips fluent API: ZipUtil.unpack rejects entries that escape the destination, but Zips uses a separate implementation with no check, so an entry named ../x can be written outside the target. The Gradle plugin com.gradleup.shadow had a Zip Slip in ShadowCopyAction the same day.

💡 Why it matters to you: If your Spring app unzips user uploads (CSV bundles, theme packs), a single unchecked Files.copy can overwrite files outside the folder.
Read deeper

The zt-zip advisory shows a CVSS 3.1 of 8.2, EPSS 0.242%, and the fix in 1.18.0. A related zt-zip issue (CVE-2026-63499) lets unpacking change output directory permissions. The recommended fix is a canonical-path check before every write.

Path target = dest.resolve(entry.getName()).normalize();
if (!target.startsWith(dest.normalize())) throw new IOException("zip slip: " + entry);

snappy-java heap overflow (CVE-2026-93451) and Guava deserialization DoS (CVE-2026-102554)

GitHub Advisories GHSA-gwq9-9ffj-mvrv and GHSA-xxph-c9ww-hj94 · updated Oct 27, 2026

snappy-java 1.1.10.8 and earlier write up to 7 bytes past the end of a Java array in its typed-array uncompress*Array methods (High, CVSS 7.5; fixed in 1.1.10.9). Guava through 33.7.1 allocates arrays sized from an unvalidated serialized value in CompactHashMap and friends, so a 72-byte stream can cause an OutOfMemoryError (fixed in 33.7.2).

💡 Why it matters to you: Both libraries sit deep in Kafka, Hadoop and Spring dependency trees; your mvn dependency:tree likely contains them.
Read deeper

snappy-java workaround: check Snappy.uncompressedLength(input) is a multiple of the element size first. Guava only matters if the application calls ObjectInputStream.readObject() on attacker-reachable data, so the real fix is to stop Java-deserialising untrusted input.

Dates: these advisories are from Oct 27; I include them because dependency scanners will flag them this week.

React Hook Form 7.92.0: about 30 fixes, and v8 beta moves to subscribe() and key

react-hook-form/react-hook-form · v7.92.0 (Nov 11), v8.0.0-beta.5 (Oct 23)

7.92.0 is a fix-heavy patch: less form-state cloning in useFormState and Controller, correct dirty state in setValues, stale async form-level validation fixed and better handling of disabled radio and checkbox inputs in useFieldArray. The v8 beta syncs these and adds React Compiler compatibility.

💡 Why it matters to you: v8 breaks common code: the useFieldArray id becomes key, watch(callback) is removed for subscribe() and any becomes unknown in public types.
