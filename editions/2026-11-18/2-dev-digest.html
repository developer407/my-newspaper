Hibernate ORM 8.0.0.CR1: Jakarta Persistence 4.0, EntityAgent and a new flush model

Hibernate (GitHub / In Relation To) · Nov 12, 2026

Hibernate ORM 8.0.0.CR1 is the first release candidate of the 8.0 line. It targets Jakarta Persistence 4.0 and Jakarta Data 1.1 and runs on Java 17, 21, 25 or 27, according to the project's release page.

💡 Why it matters to you: If your Spring Data JPA services sit on Hibernate, 8.0 is the next major you will meet, so reading the migration guide now saves a rushed upgrade later.
Read deeper

Per the project's announcement, the headline JPA 4.0 additions are EntityAgent (a standard version of what Hibernate's StatelessSession did), type-safe options for session creation, persistence operations and queries, and entity listeners declared at package or module level. Query and transaction timeouts now use the jakarta.persistence.Timeout class.

One breaking change was called out in coverage: the jakarta.persistence.validation.group.pre-persist property was previously enabled by default. This is a release candidate, so treat it as a preview and read the 8.0 Migration Guide before pointing a real project at it; the GitHub release notes themselves only link to the guides and a Jira query.

Spring for Apache Pulsar moves to the Apache Software Foundation

Spring Blog · Nov 10, 2026

Spring for Apache Pulsar becomes a subproject of Apache Pulsar and will be renamed Apache Pulsar support for Spring. Version 2.0.8 is the last release under the Spring umbrella and Spring will stop publishing patches for it.

💡 Why it matters to you: If any of your services use the Pulsar starter or the Spring Cloud Stream Pulsar binder, you will need to change dependency coordinates and imports to get future fixes.
Read deeper

The Spring Boot starter will no longer be maintained by Spring; 2.0.8 stays available with Spring Boot 4.2.0. The Pulsar binder ships in Spring Cloud Stream 5.1.0 and after that should come from the new project.

Existing applications can keep running on 2.0.8 and the 5.1.0 binder, but anything that needs new features or security fixes must switch to the new project's coordinates and package names.

Node.js security releases: 16 CVEs fixed in v26.13.1, v24.22.3 and v22.23.5

Node.js · Nov 11, 2026

The Nov 11 releases fix 16 vulnerabilities, 7 High, 6 Medium and 3 Low, across the 22, 24 and 26 lines, mostly in HTTP/2 and TLS. End-of-life lines such as Node 20 are also affected and get no fix.

💡 Why it matters to you: Any Express, NestJS or Socket.IO service you run on Node needs to be on 22.23.5, 24.22.3 or 26.13.1 or newer, especially if it terminates HTTP/2 or TLS itself.
Read deeper

Several High items are memory-safety bugs in HTTP/2 (CVE-2026-123863, -123865, -123866, -123874), plus a use-after-free from a zero-length TLS write re-entering llhttp (CVE-2026-123864). CVE-2026-123872 lets a TLS 1.2 client change servername during renegotiation and bypass client-certificate auth.

Medium items include TLS session reuse across different CA policies in https.Agent (CVE-2026-123877), proxy credentials exposed in error messages (CVE-2026-123871) and CA-only SNI contexts falling back to the default client CA (CVE-2026-123867). The release also updates llhttp, undici and sqlite. If a reverse proxy terminates TLS in front of Node, your exposure is smaller but upgrade anyway.

Security

Java4Shell (CVE-2026-114938): a Base64 decoder bug in OpenJDK that can give pre-auth RCE

CISA / Oracle / security vendors · Nov 17, 2026

CISA urged immediate patching of a critical HotSpot flaw dubbed Java4Shell. A malformed Base64 input hits the x86-64 AVX-512 Base64 decode intrinsic and writes 62 bytes past a buffer, reportedly allowing remote code execution; it is rated 9.2 on CVSS 4.0.

💡 Why it matters to you: Spring Boot services that decode Base64 from untrusted input, for example JWTs, basic-auth headers and uploads, may be exposed on AVX-512 VBMI hardware until the JDK is patched.
Read deeper

Researchers say the bug needs a CPU with AVX-512 VBMI; ARM64 and chips without VBMI are reported unaffected, and Java 8 and 11 never had the intrinsic. Sources differ on the affected range: Endor Labs lists OpenJDK 17.0.6 and later plus 18 and above, including 21, 25 and 27.

Oracle's November Critical Patch Update (Nov 17) is the main fix; secondary sources list builds ending in .1 but verify against Oracle or Adoptium. The CVE mapping was not yet fully confirmed at publication. Most-cited workaround: -XX:-UseBASE64Intrinsics (slower for heavy Base64 work). No in-the-wild exploitation was reported as of Nov 17.

# temporary mitigation reported by vendors (slower Base64)
java -XX:-UseBASE64Intrinsics -jar app.jar

AWS Advanced JDBC Wrapper CVE-2026-14265: Java deserialization RCE through the shared query cache

AWS Security Bulletin · Nov 17, 2026

The RemoteQueryCachePlugin in AWS Advanced JDBC Wrapper 3.3.0 through 4.0.0 deserializes cached query results from Redis or Valkey without class filtering. An attacker with write access to the cache could run code on the application server; the fix is version 4.0.1.

💡 Why it matters to you: If a Spring Boot service uses this wrapper with Aurora and a shared cache, treat your Redis or Valkey instance as part of the attack surface.
Read deeper

The plugin is off by default. AWS advises upgrading or disabling it and limiting cache write access to trusted principals. CVSS scores differ across sources (7.5 versus 8.8); no exploitation was reported.

OpenCVE also lists CVE-2026-18061, an XXE issue in the same plugin fixed in 4.3.0, which I did not verify against the AWS bulletin.

A study accepted at USENIX Security 2026, from a team including Ruhr University Bochum, found every one of 103 passkey-enabled sites had at least one implementation flaw. Only 71 of 208 sites asked for an extra check when a passkey was added.
