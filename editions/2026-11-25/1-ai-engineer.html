Human in the loop with Spring AI 2.1: approve a tool call, even after a restart

Spring blog by Christian Tzolov · Nov 24, 2026

Spring AI 2.1 adds tool call confirmation: mark a tool with @Tool(requiresConfirmation = true) and the loop runs unmarked tools normally but pauses when the model asks for a marked one. A banking demo asks for approval before collecting a failed mortgage payment, and the approval can come minutes later from another instance.

💡 Why it matters to you: This is exactly the pattern you need for any agent that moves money or sends messages, and it pairs naturally with Razorpay-style payment tools.
Read deeper

Without extras you handle the pause yourself: read chatResponse(), check ToolCallDecisions.awaitingDecision(reply), collect a decision per call, then call toolCallingManager.executeToolCalls(prompt, reply, decisions). The paused reply must live in durable storage that end users cannot modify.

Spring AI Session Extensions (community project, version 0.11.0, API may change) add a turn status so a parked turn can be resumed by session id from another process. The post lists known limits: no lease on dead processes, and decisions match calls by key, which can misfire with models that omit tool call IDs. Always verify the approver is allowed to approve each call.

@Tool(description = "Collect a payment", requiresConfirmation = true)
String collectPayment(String loanId, BigDecimal amount) { ... }

// pause check
var pending = ToolCallDecisions.awaitingDecision(reply);

Research, evals and startups

Paper explained: is complex agentic memory worth it, or is naive RAG stronger than we thought?

arXiv 2610.30755 and related NeurIPS poster (search-sourced) · Oct 2026

The paper "Is Complex Agentic Memory Always Needed? Naive RAG Is Stronger Than We Thought" compares plain retrieval against more elaborate agent-memory systems. A related NeurIPS 2026 poster, "RAG in a Trenchcoat", argues that minimal RAG memory matches complex systems on standard benchmarks and that those benchmarks cannot tell them apart.

💡 Why it matters to you: Before building fancy memory (or consolidation jobs) for your agents, test a verbatim RAG baseline over the chat history with pgvector; it may already be enough.
Read deeper

I could only see the titles and search summaries, not the full text, so read the PDFs for numbers. A third paper, MemDelta (arXiv 2606.29914), reports that agent self-memory underperformed basic retrieval and recommends a verbatim RAG baseline with a named embedding model plus a random-retrieval control.

The shared message is about evaluation hygiene: include simple baselines, or any memory method will look better than it is.

Paper pick: "Correct Answers from Insufficient Histories", a controlled study of agent memory evaluation

arXiv 2611.11840 (search-sourced) · Nov 2026

This November paper studies how agent memory is evaluated, with a controlled setup in which answers can be correct even when the retrieved history is insufficient. The title points at a flaw in many memory benchmarks: scoring the final answer alone can reward guessing.

💡 Why it matters to you: When you evaluate your RAG or memory features, check retrieval evidence as well as the final answer, or your scores will look better than your system.
Read deeper

The search returned only the reference list, so I cannot summarise the method or numbers; treat this as a pointer. Its references cite work on memory retrieval, compaction and failure tracing and the RAGAS paper.

A cheap habit that follows from the title: log which memory chunks were retrieved for each eval question, and score retrieval and answer separately.
