Repo: spring-ai-community/spring-ai-agent-utils — Claude Code-style tools and skills for Spring AI (686★, Apache-2.0)

github.com/spring-ai-community/spring-ai-agent-utils · updated Nov 15, 2026 · BOM 0.13.0

A Java library that reimplements core Claude Code capabilities as Spring AI tools: file read/write/edit, shell with background processes, grep/glob, smart web fetch and Brave search, an ask-the-user tool, Markdown-defined skills, subagents via a task tool (with an A2A module for remote agents), TodoWrite, file-based auto-memory and an interrupt advisor. Requires Java 17+, Spring Boot 3.x or 4.x and Spring AI 2.0.0 or later.

💡 Why it matters to you: This is the 'build your own Claude Code in Java' starter — a ready-made tutorial series for your channel.

It is in the Spring AI community org, not the core project, so versions will move. The README example wires TaskTool, SkillsTool, ShellTools, FileSystemTools, GrepTool, GlobTool and TodoWriteTool as default tools on a ChatClient.

Security note: shell and file tools give the model real power — run examples in a sandbox directory or container and use the approval features in Spring AI 2.1.

Repo: NVIDIA/SkillEvaluator — validate, de-duplicate and live-test agent skills (1.8k★, Apache-2.0)

github.com/NVIDIA/SkillEvaluator · trending Nov 16, 2026 · experimental

A three-tier framework for agent skills: Tier 1 validates safety and format, Tier 2 detects overlapping guidance using embeddings, Tier 3 runs agents with and without the skill in a sandbox (Docker via Harbor) to see whether it helps. A static quality check gives a score out of 100 with a letter grade (the example scored 86.2, B; default pass threshold 70).

💡 Why it matters to you: Skills are now a distribution format (Agent Skills was donated to the Agentic AI Foundation in October) — a CI quality gate for them is a new, teachable niche.
Read deeper

Tier 1 needs no API key; full static coverage wants external scanners such as SkillSpector and Gitleaks. The model-backed rubric check needs an NVIDIA Build API key.

Learn this today

Learn today: choosing and tuning a pgvector index — HNSW vs IVFFlat, m, ef_construction and ef_search

Evergreen · pgvector docs; relevant to Spring AI's pgvector store and Qdrant 1.20 HNSW work this week

Spend 30 minutes on the two index types pgvector offers. HNSW is the default choice: better recall/speed trade-off and no training step, at the cost of slower builds and more memory. IVFFlat builds faster but needs data in the table first and a sensible lists value. Then learn the three knobs that matter for HNSW: m, ef_construction and the query-time hnsw.ef_search.

💡 Why it matters to you: Every RAG app you build on Spring AI + pgvector lives or dies on recall and latency — this is the one tuning skill that transfers to Qdrant too.
Read deeper

Exercise: load 100k embeddings, build an HNSW index with defaults, measure recall@10 against an exact scan, then raise ef_search until recall hits 0.95 and record the latency. Repeat with IVFFlat.

Interview angle: be ready to explain why filtered vector search (metadata filters) can hurt recall, and how partial or partitioned indexes help.

CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE items (id bigserial PRIMARY KEY, embedding vector(1536));
CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
SET hnsw.ef_search = 100;
SELECT id FROM items ORDER BY embedding <=> '[...]' LIMIT 10;
