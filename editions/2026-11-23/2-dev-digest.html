Node.js security releases: 16 flaws, 7 HIGH, mostly HTTP/2 and TLS

Node.js project advisory · Nov 11, 2026

Node.js 26.13.1, 24.22.3 and 22.23.5 fix 16 vulnerabilities (7 high, 6 medium, 3 low). The HIGH ones include a use-after-free that leaks heap memory into response bodies (CVE-2026-123864), several HTTP/2 teardown bugs and a TLS 1.2 renegotiation bypass of client-certificate auth (CVE-2026-123872).

💡 Why it matters to you: Any Express or Socket.IO server that terminates TLS or HTTP/2 in Node should be on the patched line, and end-of-life versions are affected by definition.
Read deeper

All seven HIGH issues were reported as remotely exploitable by unauthenticated clients, and the HTTP/2 ones apply over TLS and cleartext. The release also updates llhttp, undici and sqlite. Medium items include proxy credentials in error messages (CVE-2026-123871) and https.Agent session reuse bypassing certificate policy (CVE-2026-123877).

If you cannot upgrade immediately, terminating TLS at nginx or a cloud load balancer reduces exposure to the TLS bugs, though not to every HTTP/2 issue.

node -v            # want >= 26.13.1, 24.22.3 or 22.23.5 for your line
npm i -g n && n lts   # or use your version manager

Security

Java4Shell (CVE-2026-114938): a critical OpenJDK Base64 decoder flaw, patched Nov 17 (search-sourced)

Qualys, Sonatype, Dark Reading, JFrog · Nov 17, 2026

Researchers at Calif named a critical memory-corruption flaw in OpenJDK's Base64 decoder Java4Shell. Reports say it chains to pre-authentication code execution in JFrog Artifactory, Jenkins, Keycloak, Jira, Confluence and PingFederate, and to post-auth exploitation in Kafka, Solr and Elasticsearch.

💡 Why it matters to you: Your Spring Boot apps run on the JDK, so update the runtime and base images; a dependency scan will not catch it because the bug is in the JDK itself.
Read deeper

Oracle and OpenJDK released fixes on Nov 17, and CISA urged immediate patching. One source lists OpenJDK 17.0.6 and later (including Oracle, Corretto, Temurin, Microsoft, Azul and Red Hat builds) as affected, while another says Java 7, 8 and 11 do not contain the vulnerable decoder. Scores differ: CVSS 4.0 of 9.2 in some reports and CVSS 3.1 of 8.1 in the OpenJDK advisory.

Distributions ship fixes on their own schedules, so check your vendor's build number, rebuild container images and keep Josh Long's 'update your JVMs' warning in mind. I could only reach summaries, not the advisory text, so read the vendor page for exact fixed versions.

java -version                      # compare with your vendor's fixed build
docker build --pull --no-cache -t myapp .   # pick up a patched base image

Spring Security 7 migration traps: strict JWT typ checks and CSRF on by default (search-sourced)

Spring Security docs and migration guides · 2026

Search results on Boot 4 and Spring Security 7 say the default JWT type check is stricter: JwtTypeValidator.jwt() requires the typ header to be JWT or absent, so RFC 9068 'at+jwt' access tokens fail unless you register a validator. The same sources say REST APIs often return 403 after upgrade because CSRF protection is now on by default.

💡 Why it matters to you: If your Spring Boot API validates JWTs from an authorization server, test with real tokens right after the Boot 4 upgrade, because 401s and 403s are the most common surprise.
Read deeper

Spring Security 7 also uses Jackson 3 for the authorization server and the oauth2 starters were renamed with a security- prefix, with the old names deprecated. The OAuth2 client properties under spring.security.oauth2.client were restructured, so diff your application.yml against the new reference.

I could not confirm every claim against the official migration guide, which is the right page to read before upgrading.

// allow RFC 9068 access tokens (typ: at+jwt) - check the reference for the exact class in your version
OAuth2TokenValidator<Jwt> v = new DelegatingOAuth2TokenValidator<>(
    JwtValidators.createDefaultWithIssuer(issuer),
    new JwtTypeValidator("at+jwt"));
decoder.setJwtValidator(v);

Auth in 2026: passkeys for login, JWTs for APIs, httpOnly cookies for browsers (search-sourced)

Clerk, WorkOS and DEV guides · 2026

Guides agree on a pattern: use passkeys as the primary login, issue short-lived JWTs for API access, keep tokens in httpOnly Secure SameSite cookies rather than localStorage and use server-side sessions where you need revocation. FIDO is cited as estimating around 5 billion passkeys in use.

💡 Why it matters to you: It matches the Spring Security and React stack you teach: passkey registration is already in Spring Security's default pages, and cookie-based sessions avoid the localStorage XSS trap.
Read deeper

Clerk notes that passkeys solve phishing but not account recovery, which stays the weak spot. Remember that OAuth is authorization and OpenID Connect adds authentication, so an access token is not proof of identity. One article claims 'OAuth3' replaces OAuth2, which I could not verify and would ignore.

Figures are vendor-sourced. For standards, read the OAuth 2.1 draft and the W3C WebAuthn spec.
